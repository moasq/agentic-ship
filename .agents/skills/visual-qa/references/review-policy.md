# Visual-review evidence policy

This reference explains what the local evidence commands prove and how to repair their
failures. The declared UI-quality rules in `AGENTS.md` remain authoritative.

## Artifact model

| Artifact | Purpose | Authored or generated |
| --- | --- | --- |
| `.agents/ui/plan.json` | Product-specific intent, explored directions, selected refinement, surface matrix, and constraints | Authored and reviewed before implementation |
| `.agents/ui/evidence/captures/*.png` | Stable local screenshots for every declared route, state, theme, and viewport | Generated from public or synthetic local state |
| `.agents/ui/evidence/draft.json` | Capture-session receipt, browser-audit results, paths, and screenshot hashes | Generated by capture |
| `.agents/ui/evidence/index.html` | Compact gallery for side-by-side inspection | Generated by capture |
| `.agents/ui/evidence/manifest.json` | Accountable acceptance bound to the plan, current sources, and current capture session | Generated by acceptance after review |

The capture matrix always includes widths 320, 768, and 1440. A plan can add evidence
but cannot silently remove those widths. A surface can declare one theme or both; a
single-theme product records that decision explicitly.

## Content-derived staleness

The completion check recomputes three independent fingerprints:

1. **Plan fingerprint** — canonical content of the complete validated plan.
2. **Source fingerprint** — paths and bytes of current authored app, component, site
   identity, and public visual inputs.
3. **Evidence fingerprint** — ordered screenshot hashes plus browser audits and
   interaction results.

The accepted manifest must match all three and the current capture-session id. File
timestamps are not evidence: they differ across operating systems and can be changed
without changing content. A screenshot path is also resolved inside the dedicated
capture directory, so a prefixed path cannot escape that boundary.

Acceptance refuses a capture session already represented by the current manifest. To
accept another visual update, regenerate the full matrix and inspect it again.

## Automated browser audit

For every matrix entry, capture checks:

- the local route returned successfully and the state's named marker became visible;
- exactly one main landmark and exactly one visible level-one heading;
- headings do not skip levels;
- visible images have an `alt` attribute;
- visible links and buttons have names;
- visible fields have labels;
- semantic headings and controls do not gain non-empty `::before` or `::after` text on
  themselves or descendants, which can duplicate an accessible name;
- the document declares a language;
- document width does not overflow the viewport;
- every declared meaningful interaction can be reached by sequential keyboard
  navigation.

The capture context explicitly sets the declared color scheme and reduced-motion
preference. It waits for local fonts and current images, then removes animation and
transition timing before the screenshot. Stable rendering makes a diff useful; it does
not make visual judgment automatic.

## Subjective review

Apply the visual-direction rubric to the gallery. At minimum, inspect product
specificity, content hierarchy, realistic content, typography, palette, density, shape
language, component-source residue, assets, responsive re-composition, interaction
states, accessibility, motion restraint, theme intent, and the single signature
element.

Record `pass`, `concern`, or `blocker` with reasons. Do not average them. A blocker is a
repair; a concern is retained review context; a pass names the visible decision that
succeeded.

Automated checks can safely reject missing coverage, stale files, accessibility
skeleton defects, overflow, and missing keyboard reachability. They cannot safely decide
whether a composition is distinctive, a type choice is culturally right, an asset is
credible, or a visual idea fits the product. Those remain accountable review decisions.

## Failure interpretation

| Failure | Meaning | Repair |
| --- | --- | --- |
| `ui-plan` | Authored UI has no valid implementation contract | Complete direction exploration and plan decisions; run `pnpm ui:plan check` |
| `ui-evidence-missing` | A declared matrix entry or screenshot file does not exist | Repair local fixtures or route reachability, then recapture the full matrix |
| `ui-evidence-mismatch` | Screenshot bytes, matrix metadata, or viewport identity changed | Diagnose the source of the visual difference and recapture; never edit hashes |
| `ui-browser-audit` | Accessibility, overflow, state, or keyboard evidence failed | Reproduce the exact entry, repair source semantics or layout, and recapture |
| `ui-evidence-stale` | Plan or authored source content changed since capture | Recapture after the source reaches its intended state |
| `ui-review` | Named acceptance evidence is absent or malformed | Inspect the gallery, then accept with specific responsibility and rationale |
| `ui-review-stale` | Acceptance belongs to older plan, sources, captures, or session | Review newly generated evidence and accept it explicitly |

## Command receipt

Use this order after a UI implementation or repair:

```text
pnpm ui:plan check
pnpm ui:review capture --base-url http://localhost:3000
pnpm ui:review accept --reviewer "<name>" --responsibility "<role or area>" --reason "<review decision>" --changed "<surface summary>"
pnpm ui:review check
pnpm check:ui
pnpm verify
```

Use `pnpm verify:full` for release-bound work.
